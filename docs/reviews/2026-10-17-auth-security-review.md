## 指摘事項

### 1. 本番メール送信がコンソール出力へフォールバックする

`authEnv.mailMode()` は `MAIL_MODE=smtp` の場合以外を `console` として扱う。コンソールモードではメール本文全体がログに出力される。招待、デバイス招待、パスワード再設定などの本文には、認証や資格情報変更に利用できるトークン付き URL が含まれる。

環境検査は `MAIL_MODE=smtp` が明示された場合に SMTP 設定を確認するが、本番で `MAIL_MODE` が未設定または誤った値でも起動を拒否しない。そのため、設定ミスやログ閲覧権限の過剰な付与により有効なリンクが漏れるおそれがある。

**推奨対応**

- 本番では `MAIL_MODE=smtp` を必須にし、未設定または不正値なら起動を拒否する。
- 認証 URL やトークンをログに出力しない。
- SMTP 設定の不足・誤りを本番起動時に検出する。

### 2. ワンタイム値の消費が原子的でない

チャレンジの `takeEntry` は Redis `GET` の後に `DEL` を実行する。マジックリンクの `consume` も、有効性の読み取り後に削除する。複数リクエストが同時に読み取りを通過すると、同じ値を複数回取得できる競合がある。

パスワード再設定確認も、トークンの有効性確認とパスワード更新・全セッション失効を行った後で保留トークンを無効化するため、並行実行で複数処理が同じリセットトークンを受理する余地がある。実害には有効なトークンと同時リクエストが必要だが、ワンタイム利用の保証が崩れる。

**推奨対応**

- Redis の `GETDEL`、Lua スクリプト等により、読み取りと消費を原子的に行う。
- パスワード再設定では、トークン消費の成功を一度だけ確定してから状態変更を行う。失敗時の整合性も考慮する。
- 同一トークンを並行使用するテストを、チャレンジ、マジックリンク、パスワード再設定に追加する。

### 3. レート制限の送信元 IP がリクエストヘッダー依存

認証・再設定・メール変更の一部で、クライアント IP として `X-Forwarded-For` を直接使用している。このヘッダーを信頼できるリバースプロキシが必ず上書きする構成でなければ、利用者が値を変更してレート制限キーを分散させられる。

また、パスキーの `/login/passkey/options` と `/login/passkey/verify` には、同ファイル内のパスワードログイン等と同等の明示的なレート制限が見当たらない。`/magic/resend` は未認証で利用でき、処理時にユーザーの既存セッションを失効させるため、IP 偽装等で制限を回避できる構成では、対象アカウントへのセッション失効を繰り返される可能性がある。

**推奨対応**

- 信頼するプロキシを明示し、そのプロキシが上書きした接続元情報のみを使用する。クライアント提供の転送ヘッダーを無条件に信頼しない。
- IP とアカウント等、複数の識別軸を組み合わせた制限を検討する。
- パスキー options／verify と、セッション失効を伴う再送処理にも適切なレート制限を設ける。

## 仕様として認識しておく点

`POST /login/method` は登録済みメールアドレスに対してログイン方式を返し、未登録アドレスには別の応答を返すため、メールアドレスの存在確認に利用できる。これは現行仕様にも記載された挙動である（`docs/specification.md` の API 概要）。アカウント列挙を許容しない要件であれば、応答内容・ステータス・タイミングをそろえる必要がある。

## 確認できた対策

- セッション Cookie は `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/` を設定し、`__Host-` 接頭辞を使用している。
- セッション等のランダムトークンは十分な乱数から生成し、Redis にはハッシュをキーとして保存している。
- API の変更リクエストでは認証サーバーと一致する `Origin` を検証している。
- WebAuthn の検証では期待する Origin と RP ID を指定している。

## 確認範囲・制約

本レビューはソースと仕様の静的確認であり、稼働中の本番環境、ログ閲覧権限、プロキシ設定、Redis のアクセス制御や TLS、デプロイ済み環境変数は検証していない。脆弱性の再現試験も実施していない。
