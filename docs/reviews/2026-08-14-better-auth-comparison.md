# Better Auth を使う場合との比較（2026-08-14）

**日付**: 2026-08-14  
**対象**: astro-user-webauthn プロジェクト  
**比較対象**: [Better Auth](https://www.better-auth.com/)（TypeScript 向け認証ライブラリ）

## 概要

本ドキュメントは、現行の自前認証を [Better Auth](https://www.better-auth.com/) に置き換えた場合に何が得られ、何が失われるか、また現行仕様を維持できるかを比較したレビューである。仕様の正本は [specification.md](../specification.md) である。

## 結論

現行仕様を維持するなら、Better Auth への移行は投資対効果が低い。

Better Auth は、パスワード・マジックリンク・パスキー・OAuth などをプラグインで追加できる汎用認証基盤である。本アプリの価値は、こうした汎用的な機能群ではなく、招待制でパスキーへ移行する際の状態遷移と制約の組み合わせにある。同じ制約を Better Auth で再現するには hook による追加実装が必要となり、独自仕様を実現するコード量はあまり減らない。一方で、スキーマ・ルーティング・結合テストは大幅な書き換えが必要になる。

## 比較の前提

本アプリの認証は次のライフサイクルで固定されている。

```text
未登録 → 管理者招待（User 作成）→ 初回のみメール認証 → パスキー必須
     → 以降はパスキーのみ → 復旧時は全パスキーを破棄
```

Better Auth の既定は、複数のログイン手段からユーザーが選択する方式である。パスキーは追加の認証手段として扱われ、登録後も他の手段は自動的に無効化されない。マジックリンクは、リンクのクリックによってログインする仕組みが既定である。

## 項目別比較

### 1. 認証モデル

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| 位置づけ | パスキー必須の閉鎖系。認証手段をライフサイクルの段階ごとに限定 | 複数の認証手段をプラグインで追加 |
| パスキー登録後 | パスワード・マジックリンクを拒否 | 他の手段も残る。無効化するには `before` hook が必要 |
| 自己登録 | なし。管理者が User を先に作る | 既定では自己登録が可能。`disableSignUp` などで制限 |
| 初回ログイン | 招待マジックリンク（seed 管理者のみパスワード） | 汎用マジックリンク／パスワード／パスキー |

現行実装では、メールアカウントが侵害されても通常のログインは許可しない、という脅威モデルが一貫している。Better Auth で同じ制約を設けるには、認証ポリシーを hook で再現する必要がある。

### 2. メールとトークン消費

| 事象 | 現行実装 | Better Auth 既定 |
|------|----------|------------------|
| パスキー登録後のメール侵害 | 通常のログインは不可 | マジックリンクでログインできる場合が多い |
| デバイス招待リンクの漏洩 | パスキーを追加されるおそれがあるが、セッションは発行されない | 同等の「ログインを伴わない登録」は標準機能にない |
| メールクライアントの GET プリフェッチ | トークンは残る（確認ボタンからの POST で消費） | verify の GET でトークンが消費され、ログインが成立する可能性がある |

現行実装では、メールの用途をオンボーディングと復旧に限定している。Better Auth のマジックリンクは継続的なログイン手段である。デバイス追加時の「再認証後にメールで招待し、リンクをクリックしてもログインは成立しない」という動作は、`registration.requireSession: false` と `resolveUser` で近づけられる。ただし、再認証フラグ・TTL・ハッシュ化トークン・メール本文は引き続き自前で実装する必要がある。

### 3. 復旧

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| 最後のパスキー削除 | 不可。復旧手段はパスワード再設定に限定 | パスキー削除は標準 API。最後の 1 件を削除できない制限は自前で実装 |
| パスワード再設定時 | 全 Credential 削除、全 Session 失効、未使用招待無効化、自動ログイン、パスキー再登録必須 | パスワード更新が中心。既存パスキーは残りやすい |
| UI | 「全パスキー無効化」を警告 | 同等の警告・一括破棄は after hook で追加 |

現行実装では、デバイスを 1 台紛失した場合でも、すべてのパスキーを破棄して再登録するという復旧手順が明確である。Better Auth では、メールとパスキーがログイン手段として並立したままになりやすい。

### 4. データ配置とセッション

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| PostgreSQL | User / WebAuthnCredential / Post | `user` / `session` / `account` / `verification` / `passkey` を標準的に使用 |
| Redis | Session・challenge・招待・再設定・レート制限（TTL を設定し、使用後に削除） | 二次ストレージ。セッション用途では主にキャッシュとして使用 |
| セッション値 | `{ id, userId, createdAt }`。ロールなどは毎回 PostgreSQL から取得 | セッションにユーザー情報を含めることが多い |
| 失効 | キーを削除。`usedAt` / `revokedAt` は使用しない | DB レコード＋二次ストレージ。プラグイン利用時は session テーブルを残す必要が生じる場合がある |

現行実装の方が、短命トークンとドメインデータの境界が明確である。Redis の再起動によって未使用トークンが失われることは、仕様として許容されている。Better Auth に移行すると、Prisma スキーマの構成が認証ライブラリの設計に依存するようになる。

### 5. アプリ構造

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| API | Hono の `/auth` `/admin` `/devices` `/posts` | catch-all の `/api/auth/*` が中心 |
| ページ認可 | `getPageSession` / `redirectForAuth` | `auth.api.getSession` と Astro locals |
| ブラウザ | `src/api-client` | `createAuthClient`（React 向けクライアントあり） |
| スキーマ | Prisma のドメインモデル | CLI によるスキーマ生成・マイグレーション |
| テスト | 仕様で定めた認証ポリシーを結合テストで直接検証 | ライブラリの既定動作と hook の挙動に合わせてテストを変更 |

現行実装では、認証機能がアプリケーションの構造に従っている。Better Auth では、認証ライブラリの設計に沿ってルートとスキーマを構成することになる。クライアント SDK と Conditional UI（ブラウザの自動補完）については、Better Auth の方が充実している。

### 6. 保守と拡張

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| WebAuthn | `@simplewebauthn` を直接利用 | 内部は同じく SimpleWebAuthn |
| セキュリティパッチ | 自前（セッション、CSRF、レート制限、トークン設計） | ライブラリ側に寄せられる |
| 管理者機能 | 招待・一覧・ロール（admin / user） | ban、impersonate、セッション一覧・失効が標準 |
| 将来の認証手段 | 仕様を変更しない限り追加しない | OAuth、2FA、Organization、SSO を追加しやすい |
| ロックイン | 仕様とコードがリポジトリ内 | バージョンアップとプラグイン互換に依存 |

Better Auth の導入目的は、パスキー実装そのものを置き換えることではなく、汎用認証基盤とそのエコシステムを利用することにある。

## 移行した場合に残る自前コード

現行仕様を維持するなら、Better Auth の導入後も次の機能は hook または周辺コードとして残る。

- パスキー登録後のパスワード／マジックリンク拒否
- パスキー未設定セッションの setup / logout / me 以外拒否
- 招待専用マジックリンク（GET 非消費、POST 消費、パスキー済み拒否）
- デバイス招待（再認証必須、ログインしない登録）
- パスワード再設定時の全パスキー削除と全セッション失効
- 最後のパスキー削除禁止

結果として、ライブラリに多くの hook を追加する構成となり、独自仕様の中核は引き続き自前で実装することになる。

## 判断

| 状況 | 判断 |
|------|------|
| 現行仕様を維持するプロトタイプ／学習用途 | 移行しない |
| パスキー必須・招待制・デバイス招待を製品の差別化要因とする | 現行のまま仕様を固める |
| OAuth・2FA・組織・なりすましなどの汎用認証機能を追加する | Better Auth の利点が生じるため、その時点で再検討する |
| 認証のセキュリティ保守のみをライブラリに委ねたい | 利点はあるが、この仕様を hook で再現するコストの方が大きい |

現行仕様（招待制・パスキー必須・デバイス招待ではログインを成立させない・復旧時は全パスキーを破棄）を維持する限り、現行設計の方が制御しやすい。
