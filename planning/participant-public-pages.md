# 参加アプリの公開画面

本ファイルは、参加アプリのうち、認証サーバーにログインしていない閲覧者にも見せる画面を持つアプリの仕様です。例はブログの記事一覧と記事本文です。

引き渡し、Cookie、セッションの解決、ログアウト、オリジン検査は [participant-app.md](./participant-app.md) に従います。利用許可は [app-permissions/grant.md](./app-permissions/grant.md) に従います。本ファイルが追加するのは、参加アプリが公開と定めたパスについて、未認証の引き渡しと、付与なしの 403 と、パスキー 0 件の誘導を適用しないことだけです。要入場の画面は [participant-app.md](./participant-app.md) のままです。

認証サーバーは参加アプリのリクエストを受けません。公開画面を出すかどうかは、参加アプリがパスごとに決めます。`App.defaultPermission` の `allow` は、登録済みで実効許可が `allow` の利用者を入場させる値です。アカウントを持たない閲覧者には効きません。

## 1. 画面の分類

分類はサーバー側の固定です。クエリやクライアントの指定では変えません。分類に無いパスは要入場です。

| 分類 | 例 | 未認証の GET / HEAD | 更新 |
|------|-----|----------------------|------|
| 公開 | `/`、`/posts/:id` | 200 で本文を返す。引き渡しを開始しない | 公開の更新口は作らない |
| 要入場 | `/posts/new`、`/roles`、`/account` | [participant-app.md](./participant-app.md) セクション 4 の引き渡し | 401「ログインが必要です」。引き渡しは開始しない |
| 引き渡しの例外 | `/callback`、`/logged-out` | [participant-app.md](./participant-app.md) のとおり。公開にはしない | 同左 |

公開は GET と HEAD だけです。POST、PUT、PATCH、DELETE は要入場です。`POST /logout` は [participant-app.md](./participant-app.md) セクション 8 で、公開画面からでも送れます。

## 2. 公開画面でのセッション

認証サーバーの Cookie は参加アプリのホストに届きません。`Domain` は付けません。認証サーバーにだけセッションがある閲覧者は、引き渡しが終わるまで参加アプリでは未ログインです。

公開の GET / HEAD は、次の順で扱います。要入場の画面では、パスキー 0 件と付与なしを [participant-app.md](./participant-app.md) セクション 3 の 302 と 403 に戻します。

```text
__Host-session が無い
  → 未ログインとして本文を返す。引き渡しは開始しない
  ↓
セクション 3 の検査でキーが無い、JSON でない、appId が違う、
User が無い、disabledAt がある
  → Cookie とセッションの破棄はセクション 3 と同じ
    破棄したあと、未ログインとして本文を返す。引き渡しは開始しない
  ↓
WebAuthnCredential が 0 件
  → setup-passkey へは送らない
    TTL も Cookie の Max-Age も延ばさない
    未入場として本文を返す
  ↓
実効許可が allow 以外
  → 403 にしない
    Cookie は残す。TTL も Cookie の Max-Age も延ばさない
    未入場として本文を返す。ログアウトは通す
  ↓
パスキーがあり、実効許可が allow
  → 入場済み
    EXPIRE と Cookie の Max-Age の更新はセクション 6 と同じ
    本人向けの表示と、アプリ内ロールに応じた操作を出してよい
```

未入場の公開画面には、投稿、編集、その他の本人に紐づく更新を出しません。ログアウトは、破棄していないセッション Cookie が残っているときだけ出します。

無効化、付与の削除、パスキーの削除は、次のリクエストから効きます。セッションの作り直しは要りません。

## 3. ログインへの誘導

公開画面を開いただけでは `__Host-handoff` を発行しません。認証サーバーへは送りません。

「ログイン」のように、入場を求める操作のときだけ [participant-app.md](./participant-app.md) セクション 4 を実行します。戻り先は、その時点の公開パスです。パスの検査は同セクションのままです。`/login`、`/callback`、`/logged-out` は戻り先にせず `/` にします。ブログでの入口はセクション 6 です。

認証サーバーにセッションが無い閲覧者は、引き渡し URL に着いたあと、認証サーバーが自分のログインへ送り、成功後に同じ引き渡しへ戻します。Credential が 0 件のセッションは `/setup-passkey` に留まり、コードを発行しません。アプリ未登録、`redirect_uri` の不一致、実効許可が付与なしのときは、認証サーバーが 403「引き渡し先のアプリを利用できません」を返し、参加アプリへは戻りません。公開画面へ戻す処理は参加アプリに置きません。

## 4. 応答に含めるもの

公開画面が返す行は、そのアプリが公開と定めた業務データだけです。下書きや限定の行は公開のクエリに含めません。行が無いときは 404 です。ログインへの 302 や、権限の 403 にはしません。

業務テーブルは参加アプリの所有です。共有の `User` には書きません。公開の読み取りにアプリ内ロールは要りません。作成と更新は、入場のあと、このアプリが `User.id` に持つアプリ内ロールで判定します。共通 `admin` の管理操作と、共通 `manager` のロール管理は [participant-app.md](./participant-app.md) のとおりです。

公開の本文に出してよい利用者情報は、著者として示す `User.name` だけです。`User` を読む場合も、次は出しません。

- `email`、`role`、`disabledAt`
- 他の利用者の一覧
- `AppGrant`、`defaultPermission`
- セッショントークン、引き渡しコード、Cookie の値

入場済みのとき、その本人の `email`、`name`、共通ロールを、本人向けの部分に出してよい。範囲は [participant-app.md](./participant-app.md) の `/` と同じです。

接続権限は [participant-app.md](./participant-app.md) セクション 10 のままです。公開画面のために列権限を増やしません。

## 5. キャッシュ

応答が Cookie に依存しない公開画面は、共有キャッシュに載せてよいです。入場済みと未ログインで HTML が変わる場合は `Cache-Control: private` とし、共有キャッシュに載せません。

`/callback` の `Cache-Control: no-store` と `Referrer-Policy: no-referrer` は変えません。

## 6. ブログのパス

| パス | 分類 | 内容 |
|------|------|------|
| `/` | 公開 | 公開記事の一覧 |
| `/posts/:id` | 公開 | 公開記事の本文。著者の `User.name` を出してよい |
| `/posts/new` | 要入場 | 記事の作成。アプリ内ロールで判定する |
| `/posts/:id/edit` | 要入場 | 記事の更新。アプリ内ロールで判定する |
| `/account` | 要入場 | 自分の email、name、共通ロール。ログアウト |
| `/roles` | 要入場 | [participant-app.md](./participant-app.md) の `/roles` |
| `/login` | 引き渡しの開始 | ナビゲーションの「ログイン」の入口。本文は返さない |
| `/callback` | 引き渡しの例外 | 引き渡しの戻り |
| `/logged-out` | 引き渡しの例外 | 「ログアウトしました」。このページから引き渡しを開始しない |

`/posts/:id` が公開記事で無いときは 404 です。

### 利用者

未ログインの閲覧者は `User` でもアプリ内ロールでもありません。記事の作成と更新は業務操作であり、共通 `admin` の管理操作には含めません。下書きの閲覧も公開の GET には含めず、`editor` などこのアプリが記事の作成と更新を許したアプリ内ロールだけにします。

| 利用者 | 条件 | 公開記事 | 記事の作成・更新 | アプリ内ロールの管理 |
|--------|------|----------|------------------|----------------------|
| 閲覧者 | セッションが無い | 読める | できない | できない |
| 編集者 | 入場済みかつアプリ内ロール `editor` | 読める | できる | できない |
| 管理者 | 入場済みかつ共通ロール `admin` | 読める | `editor` があるときだけ | できる |
| ユーザー管理者 | 入場済みかつ共通ロール `manager` | 読める | `editor` があるときだけ | できる |
| 入場のみ | 実効許可が `allow` だけ | 読める | できない | できない |

### ナビゲーション

- 未ログインの公開画面には「ログイン」を出します。投稿、編集、ロール管理は出しません。
- 入場済みの画面にはログアウトを出します。記事の作成と編集は `editor` のときだけ、ロール管理は共通 `admin` または `manager` のときだけ出します。
- 実効許可が付与なしで Cookie だけ残っている公開画面には、ログアウトだけを出します。
- 「ログイン」は認証サーバーへの直リンクにはしません。`/login` で `__Host-handoff` を発行してから [participant-app.md](./participant-app.md) セクション 4 の引き渡しへ 302 します。
- 戻り先は、リンクを押した公開パスです。`/login` のクエリ `return` がセクション 4 のパス検査を通るとき、それを戻り先にします。無い、または検査を通らないときは `/` です。`/login`、`/callback`、`/logged-out` は戻り先にせず `/` にします。
- リンクの有無は表示だけです。作成と更新は、サーバーがアプリ内ロールを確認したときだけ実行します。

## 7. 必須事項

- 公開画面の GET / HEAD から引き渡しを開始しない
- 公開の更新口を作らない
- 付与なしとパスキー 0 件を、公開画面では 403 と `/setup-passkey` への 302 にしない
- 無効なセッションと、無効化されたユーザーの破棄は、公開画面でも行う
- 入場済みの表示は、パスキーがあり実効許可が `allow` のときだけ行う
- 公開の応答に `email`、権限、トークンを出さない
- `defaultPermission = allow` を、未ログインの閲覧許可として使わない
- セッション Cookie に `Domain` を付けない
- 「ログイン」は同一オリジンの入口から引き渡しを開始し、入口自身のパスを戻り先にしない
- 記事の作成と更新はアプリ内ロールで判定し、共通 `admin` だけでは許可しない
