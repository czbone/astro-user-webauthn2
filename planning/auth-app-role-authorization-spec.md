# 認証サーバーと参加アプリのロール・認可仕様

## 1. 目的

1台の認証サーバーと複数の参加アプリからなるシステムにおいて、共通のユーザー認証・管理と、各参加アプリ固有の業務権限を分離して管理する。

基本方針は次のとおり。

- 認証サーバーは、共通ユーザー、認証、セッション、共通ロール、参加アプリへの利用許可を管理する。
- 各参加アプリは、そのアプリ固有のロールと業務操作の認可を管理する。
- 共通ロールと参加アプリのロールは独立して割り当て、独立して判定する。
- 権限はロール単位で管理する。個々の操作権限をユーザーごとに直接設定する仕組みは、当面導入しない。

## 2. ロールの構成

### 2.1 認証サーバーの共通ロール

共通ロールは、次の3種類とする。

| ロール | 管理場所 | 権限・責任 |
|---|---|---|
| `admin` | 認証サーバー | 認証サーバーの基本設定、共通ユーザー管理、参加アプリの登録・設定、共通ロールの変更、全参加アプリの管理権限 |
| `manager` | 認証サーバー | 参加アプリ内のユーザーに対するロールの割り当て・変更・解除 |
| `user` | 認証サーバー | 通常の利用者。参加アプリで許可された業務を行う |

`admin` は、すべての参加アプリでアプリ管理者相当の権限を持つ。独立した `app_admin` ロールは設けない。

`manager` は、共通ロールを変更する権限を持たない。参加アプリのロール管理を担当するが、`manager` であることだけを理由に、参加アプリの業務操作権限が自動的に付与されることはない。

### 2.2 参加アプリのロール

参加アプリは、用途に応じて独自のロールを定義する。例：

| ロール | 権限・責任の例 |
|---|---|
| `modifier` | 日常の運用管理、データの変更など |
| `editor` | コンテンツの作成・編集 |
| `viewer` | 閲覧のみ |

これらは例であり、各アプリは必要なロールだけを定義すればよい。同じ名前のロールでも、アプリごとに異なる意味・権限を持たせてよい。

参加アプリのロール定義は、最初はアプリ内の固定設定として管理してよい。ロールを運用中に自由に追加・編集する要件が生じた場合に限り、ロール定義をデータベースで管理する方式を検討する。

## 3. 権限の割り当てモデル

ユーザーの権限は、次の情報を組み合わせて決定する。

1. **共通ロール**：認証サーバーで管理する `admin` / `manager` / `user`
2. **参加アプリへの利用許可**：ユーザーが対象アプリを利用できるか
3. **参加アプリのロール**：対象アプリでどの業務操作を行えるか

参加アプリのロールは、アプリごとに独立して割り当てる。例えば、あるユーザーに次の設定が可能である。

- 共通ロール：`manager`
- 参加アプリ A：`modifier`
- 参加アプリ B：`viewer`

この場合、ユーザーは参加アプリ A では運用管理を行い、参加アプリ B では閲覧のみを行う。また、共通ロール `manager` によって、許可された範囲で参加アプリのロール管理を行える。

`admin` は、個別のアプリ内ロールを割り当てなくても、すべての参加アプリで管理者相当の操作を行える。

## 4. 共通ロールの変更ルール

共通ロールの昇格・降格は、認証サーバーの `admin` だけが実行できる。

| 操作 | `admin` | `manager` | `user` |
|---|---:|---:|---:|
| `user` → `manager` | 許可 | 不可 | 不可 |
| `manager` → `user` | 許可 | 不可 | 不可 |
| `user` → `admin` | 許可 | 不可 | 不可 |
| `manager` → `admin` | 許可 | 不可 | 不可 |
| `admin` → `manager` / `user` | 許可（最後の `admin` を除く） | 不可 | 不可 |
| 認証サーバーの基本設定変更 | 許可 | 不可 | 不可 |
| 参加アプリ内のロール管理 | 許可 | 許可 | 不可 |

補足：

- `manager` は他のユーザーを `manager` に昇格できない。
- `manager` は他の `manager` を降格できない。
- `manager` は共通ロール `admin` を付与・解除・変更できない。
- `manager` は認証サーバーの基本設定を変更できない。
- 共通ロールの変更は、認証サーバー側の専用処理で検証・実行する。参加アプリから共通ロールを直接更新してはならない。

## 5. 最後の `admin` を保護するルール

システムに有効な `admin` が最低1人は存在することを保証する。

- 有効な `admin` が1人しかいない場合、そのユーザーを `manager` または `user` に降格できない。
- 有効な `admin` が1人しかいない場合、そのユーザーを削除・無効化できない。
- `admin` の降格・削除・無効化を行う際は、処理後も有効な `admin` が1人以上残ることをサーバー側で確認する。
- この確認は、管理画面の表示だけでなく、更新処理そのものでも必ず実行する。
- 同時操作によって最後の `admin` が失われないよう、トランザクションや適切な排他制御を用いて検証と更新を行う。

## 6. 参加アプリ内のロール管理

`manager` は、参加アプリにおいてユーザーのアプリ内ロールを割り当て・変更・解除できる。

- `manager` のロール管理権限は、共通ロールによって与える。
- `manager` は共通ロールを変更できない。
- `manager` は、参加アプリ内のロール管理を行えるが、それだけで `modifier` や `editor` などの業務権限を自動的に得るわけではない。
- `admin` は、すべての参加アプリの管理権限を持つ。
- 参加アプリ内ロールの割り当て・変更・解除は、参加アプリ側のサーバーで認可チェックを行う。

本仕様では、`manager` が管理できる参加アプリを個別に制限せず、すべての参加アプリを管理対象とする。

## 7. 認可処理の原則

参加アプリが保護対象の操作を実行するときは、サーバー側で次を確認する。

1. セッション等を検証し、信頼できる共通ユーザーIDを取得する。
2. 対象アプリへの利用許可を確認する。
3. 共通ロールによる特別な権限（`admin` または `manager` のロール管理権限）が必要かを判定する。
4. 業務操作の場合は、参加アプリ内ロールを確認する。
5. 許可された場合だけ操作を実行する。

画面上でボタンを非表示にするだけでは不十分であり、APIやサーバーアクションなど、実際に操作を実行する箇所でも認可を行う。

クライアントから送られたロール名や権限情報を、そのまま信頼してはならない。認証サーバーの信頼できる情報源、または適切に検証されたセッション情報を使用する。

## 8. データ管理の原則

### 認証サーバー

- 共通ユーザー
- 認証情報・セッション
- 共通ロール
- 参加アプリの登録情報と利用許可
- 共通ロールの変更履歴

### 各参加アプリ

- 共通ユーザーIDとの対応
- アプリ内ロールの割り当て
- 必要に応じてアプリ内の操作履歴

参加アプリでは、ユーザーのメールアドレスではなく、認証サーバーが発行する変更されない共通ユーザーIDを識別子として使用する。

参加アプリ内ロールは、各アプリのデータベースまたは固定設定で独立して管理する。あるアプリのロール変更が、別のアプリのロールに影響してはならない。

## 9. 変更履歴

少なくとも共通ロールの変更について、次の情報を記録する。

- 操作した管理者のユーザーID
- 対象ユーザーのユーザーID
- 変更前のロール
- 変更後のロール
- 操作日時
- 成功・失敗の結果（可能であれば失敗理由も）

参加アプリ内のロール変更についても、運用上必要であれば同様の履歴を記録する。

## 10. 仕様の要点

- 共通ロールは `admin`、`manager`、`user` の3種類。
- `admin` は認証サーバーの管理と、すべての参加アプリの管理権限を持つ。独立した `app_admin` は設けない。
- `manager` は参加アプリ内のロール管理を担当するが、共通ロールは変更できない。
- 共通ロールの昇格・降格は `admin` だけが行える。
- 参加アプリのロールは、アプリごとに独立して管理する。
- 共通ロール、アプリ利用許可、アプリ内ロールを区別して認可する。
- 最後の有効な `admin` は、降格・削除・無効化できない。
- 認可はサーバー側で実施し、共通ロールの変更履歴を記録する。
